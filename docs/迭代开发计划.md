## 交付策略

采用短周期、按用户流程切分的迭代。每轮先写可执行测试并验证预期失败，再实现功能、自动回归，最后提供可运行页面给用户验收。用户负责效果验收；环境准备、测试代码、测试运行和缺陷修复由 agent 承担。

以一个可验收小目标为一轮，不承诺固定日历工期。以下拆分是原文 I0～I6 的细化，保留全部 V1 范围。若单轮过大，继续拆分；不能以加快速度为由省略权限或保存完整性。

## 自动验证与验收门槛

每轮遵守以下顺序：

1. 写明本轮需求 ID、完成条件和验收路径；创建真实测试代码及独立、可清理的 fixtures。
2. 执行新增测试，记录功能未实现所产生的预期失败。环境错误不能计作有效失败。
3. 实现本轮最小完整功能；修复测试暴露的问题，必要重构后再次回归。
4. 运行本轮测试、受影响的已有测试、类型检查、静态检查及构建。涉及权限时运行 Firebase 规则及 callable 集成测试；涉及页面闭环时运行浏览器测试。
5. 启动验收页面，准备测试账户、样例和截图。给用户地址、简短验收步骤、测试摘要及已知限制。
6. 状态更新为“自动验证通过待验收”；用户验收通过后更新为“验收通过”并进入下一轮。验收缺陷先补回归证据、修复和复测。

不要求用户执行测试或整理技术日志。测试未运行、失败或依赖缺失时如实说明，不将局部模拟通过称为真实云环境通过。

## 测试工程组织建议

- 业务单元测试靠近功能代码，公共规则放在共享包，前后端使用相同数据合同。
- `tests/rules/`：Firestore、Storage 权限测试，覆盖匿名、创建者、其他成员、管理员。
- `tests/integration/`：模拟器中真实函数、数据和文件调用，覆盖保存、并发、清理和角色事务。
- `tests/e2e/`：浏览器用户流程、下载和必要截图；不同角色使用独立浏览器上下文。
- `tests/fixtures/`：有效／无效 Excel、文本和图片；自动生成，明确标注合成资料。真实样例只在适当脱敏后使用。
- 每次运行保存结果摘要和失败截图／追踪，交付时链接实际报告。记录需求 ID 对应的测试和验收状态。
- 初始化统一验证入口；具体命令以实际工程脚本为准，避免在本计划中宣称尚不存在的命令已经可运行。
